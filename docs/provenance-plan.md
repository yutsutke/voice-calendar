## 1. 背景（なぜこれをやるのか）

チャットでの議論の結論だけ書く。

- **アプリの価値はコードにない。** 音声入力機能そのものは、大手なら数週間で書ける。値段がつくのは「特許・チーム・ユーザーベース・時間の圧縮」のほう。
- **既存設計で最も模倣されにくいのは「フィールド単位の出所追跡」。** ハーネス（フォーム＝スキーマ＝ツール契約の同一性）は設計思想として強いが、それ自体は請求項にならない。出所追跡は技術的課題（分散データの一貫性・LLM 出力の検証可能性）に直結する。
- **2026年以降に希少になるのは「AI が読む」ではなく「AI が記録系に書き込むときの説明責任」。** 書き込みが怖いのは「どこまでが自分の意図で、どこからがモデルの推測か分からない」から。

したがって一点突破すべきは、**出所追跡を「ラベル」から「発話のどの部分から来たか」まで降ろすこと**。

### 具体例

「来週の火曜3時から打ち合わせ」という発話に対し:

| フィールド | 値 | 出所 |
|---|---|---|
| title | 打ち合わせ | 発話に直接出現（確定） |
| start_time | 15:00 | 「3時」に紐づく（確定）※ただし午前/午後は推論 |
| date | 2026-07-28 | 「来週の火曜」＋今日の日付からの推論 |
| location | (空) | 言及なし。モデルが埋めていい場所ではない |

これが効くのは3方向:

1. **確認が外科的になる** — 全部見せずに推論由来だけ聞けばいい
2. **訂正が局所的になる** — 検証失敗フィールドだけの再生成がスパン単位で成立
3. **信頼が検証可能になる** — なぜこの値なのかを発話まで遡って示せる

画面のない入力デバイス（スマートグラス等）では「全部表示して確認」が原理的に成立しないため、この設計は必然になる。

> **▶ 2026-07-22 の答え（この例はこのアプリでは起きない）**
>
> 旗艦例の `start_time 15:00 ※午前/午後は推論` は **voice-calendar では発生しない**。v0 から「修飾なしの 1〜6 時（＝「3時」）は午前/午後が決められない → **埋めない**（素通し）」が確定仕様だから（[engine/parser.js](../engine/parser.js) 冒頭コメント・[tests/parser.test.js](../tests/parser.test.js) の `明日3時 打ち合わせ` → タイトルに「3時」が残る）。
>
> つまり **SPEC §7「創作しない」が、inferred を最初から小さくしていた**。ルール経路で実際に `inferred` になるのは次の3種だけ:
> - **年・月の最近接補完**（v8）: 「6月30日」＝年を言っていない／「20日」＝月を言っていない → 実在する複数候補から1つを選んだ
> - **時刻だけで日付がない**（v0 の決め打ち）: その時刻がまだ来ていなければ今日・過ぎていれば明日 → now 比較で2候補から選んだ
> - **日またぎ**: 「22時から2時まで」の終了日を翌日にした
>
> 3方向の効き目のうち **③ 信頼が検証可能になる** は v55-57 で成立。**① 確認が外科的になる**は背骨②③（仲介者を消す・聞き返さない）と衝突しうるので、**ゲートではなく記録**として着地させた（inferred でも止めない・診断と CSV に残す）。**② 訂正が局所的**は Phase D。

## 2. 設計判断（決まったこと）

### D1. スパンは2段階に分ける

| | 内容 | API 依存 | 用途 |
|---|---|---|---|
| 文字オフセット span | transcript 文字列内の [start, end] | なし | 確認 UI・訂正・幻覚検出 |
| 時間 span | 音声の [start_ms, end_ms] | あり | 該当箇所の聞き返し |

**文字オフセットを先に実装する。** 効果の大半はこちらで得られ、音声認識 API の仕様に依存しない。時間 span は Phase C で条件付き。

### D2. LLM にオフセット数値を直接出させない

LLM に数値インデックスを出させると幻覚する。代わりに:

1. LLM には各フィールドについて **「発話中の該当する引用文字列」** を出させる
2. コード側で `transcript.indexOf(quote)` により位置を解決する
3. 見つからなければ `inferred` にフォールバックする

**この3が重要。** transcript に存在しない文字列を LLM が「引用」したら、それは幻覚であり、自動検出できる。副次効果として**幻覚検出器**になる。

### D3. 出所の分類（enum）

```
transcript   — 発話に直接出現。span あり
inferred     — 発話 + 文脈（現在日時・過去の予定・デフォルト値）からの推論。span なし
user_edit    — ユーザーがフォームで編集
external_sync— 外部カレンダーから同期
default      — スキーマ既定値
```

「3時」→ 15:00 のような **部分確定** は、値の一部が推論（午前/午後）なので `inferred` 側に倒す。安全側に倒す原則。判断に迷う場合は常に `inferred`。

### D4. 後方互換

span は optional。既存データは span なしで動き続ける。マイグレーションは不要にする。

> **▶ 2026-07-22 の答え（実装での確定）**
>
> - **D1**: 文字オフセット先行を採用。span は `{ a, b, quote }`（既存コードが `a`/`b` 命名なのでそれに合わせた）。
> - **D2**: 採用。**ただし錨（検証の基準文字列）は「アプリが自分で持っていた本文」だけ**とした——封筒の `sourceText`（AI 自身が書き写した本文）で AI の引用を検証するのは**自己証明**であり検証にならない。錨が無い経路（WebMCP）では quote 付きの値を transcript と認めず `null`（不明）にする。
> - **D3（分類を減らした）**: 実装は **`transcript` / `inferred` / `human`** の3つ。理由:
>   - `user_edit` → **`human`** に改名（このリポは v1 から `origin: 'voice' | 'human'` を持っており、語彙を増やさず既存に合わせた）
>   - `external_sync` → **存在し得ない**（iOS17 write-only ＝カレンダーを読めない・「既存予定の読み取り」は SPEC §3 で park 中）。将来 full access に格上げした時の予約語として名前だけ残す
>   - `default` → **保存アダプタの既定値は draft に入らない**（「日時なし→今」「終了なし→開始+1h」は materialize が保存の瞬間に付ける）＝フォームの欄の出所としては現れない。台帳側の関心事なので今は持たない
>   - `'?'`（出所情報なし）を**明示的に持つ**ことにした＝**不明を不明のまま数える**（`transcript` に化けさせない）
> - **D4**: 採用。prov / quotes / 台帳の prov・fix は**すべて optional**。v54 以前の来歴 snapshot・staging 行・台帳行がそのまま読める（テストで固定）。マイグレーション無し。

- [x] **使用中の音声認識 API と、その出力形式を確認する**

>
> **Phase 0 で計画に無かった発見（重要）**
>
> 1. **パーサは内部で最初からスパンで動いていた**。日付候補は `{date, a, b}`・重複は先勝ち・存在しない日付は `blocked` スパン（v8）。**捨てていただけで、持っていた**＝A' は「発明」ではなく「配管」だった。
> 2. **主経路は LLM ではない**。既定の音声→フォームは決定的ルールパーサ（SPEC §2-5）で、LLM は既定オフの脇道。→ D2（quote＋indexOf）が要るのは **AI 経路だけ**。ルール経路は**幻覚ゼロの正確なオフセットを直接出せる**＝**ルール経路が AI 経路の ground truth になる**（同じ不変条件 `quote === text.slice(a,b)` を逆向きに使う）。
> 3. **「transcript」とはどの文字列か**が論点だった。このアプリは normalize（v14・不可視文字除去）→ **辞書展開**（v37・**解釈の前**に「僕のメールアドレス」→実アドレスへ）で文字列が変形する。→ **スパンは展開後の文字列（`normalizedText`）にアンカーする**と決めた。展開自体は来歴の 🔤 が出所イベントとして既に記録している。
> 4. **同種の器官が既にあった**: 素通しの痕跡（v7）＝スパンの補集合／notes の「なぜ埋めなかったか」／AI の `ambiguities` 自己申告（v39・v43）／手直し検出（v44/v45）＝Phase B の `corrected_fields`。**計画とリポが互いを知らないまま同じ設計に収斂していた**。

### Phase A: 文字オフセット span

- [x] スキーマの provenance に `span: { start, end, quote } | null` を追加（optional）
- [x] LLM 出力契約（JSON Schema）を変更: 各フィールドに source と quote を要求する
- [x] 解決レイヤーを実装: quote → transcript 内の位置に変換／見つからなかった件数をログに出す（幻覚率の指標）
- [ ] フォーム UI: inferred のフィールドだけを視覚的に区別する

> **▶ 2026-07-22 の答え（v55 = A' / v56 = A''）**
>
> - **v55（ルール経路）**: `interpret` が `prov`（欄 → `{source, span:{a,b,quote}, why?}`）を返す。**inferred の境界を機械的に定義した**＝「実在する複数候補から1つを選んだら inferred」「定義的に1つへ解決する語は transcript」。`why` に理由（notes と同じ言葉遣い）。store は prov を**記録として**保持し、**判定には使わない**（判定の正は origin のまま＝v3 の二重管理を避ける）。`quote === normalizedText.slice(a,b)` をテストで強制。
> - **v56（AI 経路）**: 契約に `quotes`（省略可）。見つかる→ transcript（span 付き）／**見つからない→ inferred に降格＋`quoteMisses` を計数**（＝幻覚率の観測点・診断に「📎 引用の不一致 N件」）／quote 無し→ inferred（契約が「本文に無い項目は載せない」と指示している＝**載せないこと自体が推論の申告**）。
> - 🚫 **quote 不一致を `problems` に入れなかった**＝v53「まとめて入力の自動保存」の門を今は変えない。**変えるかどうかは Phase B の数字（不一致の頻度と訂正の相関）を見てから**決める（このリポの「塞ぐ時は開ける条件を書き添える」流儀）。
> - **UI 強調は作っていない**（意図的）。SPEC §3 が park している「仮置き UI」に触れる変更なので、**un-park の条件＝実データ**を満たしてから。今は診断の `📎 出所` 行と CSV だけ。

### Phase B: 計測（Phase A と同時に入れる）

登録1件ごとに記録し、追う指標は2つ:

1. **訂正率** = 訂正フィールド数 / 総フィールド数
2. **訂正のうち inferred 由来だった率**

2が高いこと（＝訂正はほぼ推論箇所に集中していること）が、この設計の正しさの証明になる。逆に transcript 由来が頻繁に訂正されるなら、quote 解決か LLM 出力契約が壊れている。

保存先はまずローカル（IndexedDB 等）で十分。母数が溜まってからバックエンドを考える。

> **▶ 2026-07-22 の答え（v57）**
>
> - 保存先は **既存の記録台帳（localStorage）＋ CSV 書き出し**にした（IndexedDB を新設しない＝v36 の CSV 経路にそのまま乗る）。行に焼くのは:
>   - `prov` = 欄 → 出所（`transcript` / `inferred` / `human` / `?`）
>   - `fix` = **人が直した欄 → 直される前の出所**（＝指標②がこの1列で出る）
> - **span は台帳に焼かない**（行が太る・集計に不要）。要るのはセッション中だけ。
> - **CSV の末尾に「出所」「訂正」列**（`title=確 startDate=推` の記法）＝表計算に貼れば指標①②がそのまま集計できる。
> - 🚫 **バックエンドに送らない**（計画の「まずローカル」を恒久方針に）。理由＝公開済み privacy「データを収集していません」と、**App Store Guideline 2.1 で AI/通信について既に照会を受けている**こと。統計値であっても送信経路を増やさない。
> - **訂正の検出**は store が `origin`（音声の値だったか）から導出＝**新しい真実を作らない**。同値の再確定は訂正でない・音声が書き直したら訂正から消える（最終値が誰のものかと一致する）。

### Phase C: 時間 span（Phase 0 の結果次第）

単語タイムスタンプが取れる場合のみ。文字オフセット → 単語インデックス → ms の対応表を作る。用途は「なぜこの値なのか」を音声で聞き返す UI。Phase A/B が回ってからでよい。

> **▶ 2026-07-22 の答え**: **native のみ可能**（`SFTranscriptionSegment.timestamp` / `.duration`）。web は標準に無い＝経路差が出る。着手は B の数字が出てから。⚠️ Swift 変更＝Codemagic ビルドが要る（Windows に Xcode なし）ので、他の native 変更と**溜めてから回す**。

### Phase D: 部分再生成の実測

スキーマ検証で落ちたフィールドだけを再プロンプトする仕組み。

- [ ] 全体再生成版と部分再生成版の両方を実装し、同一入力で比較する
- [ ] 測る: トークン数、レイテンシ、API 呼び出し回数、収束までの試行回数
- [ ] 「全体再生成比で N% 削減」という数字を出す

> **▶ 2026-07-22 の答え**: 決定0（特許を追わない）により、**「弁理士相談の前に終わらせる」という締め切りは外れた**。数字自体は依然として有用（ピッチ・設計判断）なので保留のまま。B が回って「どのフィールドがよく落ちるか」が分かってから作ると、対象を絞れて実装が小さくなる。

## 4. やらないこと（スコープ外）

- **音声認識エンジンの自作・精度改善** — OS ネイティブと Whisper 系の進化に飲まれる
- **カレンダー機能の網羅**（繰り返し予定の複雑なルール、招待者管理など） — 既存カレンダーアプリに勝つ意味がない
- **カレンダー以外のドメインへの横展開** — カレンダーで完璧になる前に広げない
- **Google Calendar 双方向同期の完成を待つこと** — span はローカルで先に実装でき、依存関係はない

## 6. 進め方の原則

- **Phase 0 が終わるまでコードを書かない。** 特にリポジトリ公開日の確認は、後から取り返しがつかない
- **Phase A と B は同時に入れる。** 計測なしの A 単体は価値が半減する
- **大きくなりそうなら分割する。** 1セッションで Phase 0 + A の途中まで、が現実的な区切り

> **▶ 2026-07-22 の答え**: Phase 0 → A' → A'' → B を**1セッション（同日）で完走**した。見積もりより速かった理由は、**既存の器官に乗れたから**（パーサ内部のスパン・origin・手直し検出・CSV 列追加の前例）。原則①は守った（Phase 0 の実測を先に出し、決定0 を取ってから着手）。原則②も守った（A と B は同日・B 無しで止めていない）。
